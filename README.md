# Структура приложения

В результате перехода на микросервисную архитектуру было создано три сервиса:
* **UsersService** отвечает за регистрацию и логин пользователя
* **EventsService** отвечает за создание, удаление, просмотр событий
* **BookingsService** отвечает за создание, удаление, просмотр броней
Каждый работает со своей базой данных. Взаимодействие между сервисами происходит по средствам обмена сообщениями через **Kafka**. За распределённый кэш отвечает **Redis**

# Потоки данных
Обмен данными между сервисами происходит по средствам **Kafka**. В сервисах Events и Booking реализованы паттерны Inbox, Outbox. Для отправки сообщения сервис помещает его в таблицу Outbox, OutboxBackgroundService обрабатывает записи этой таблицы и отправляет сообщение в соответствующий топик Kafka. На принимающей стороне KafkaConsumer кладёт данные в таблицу Inbox, а затем InboxBackground обрабатывает эту таблицу и вызывает требуемую бизнес логику 
## Создание и обработка брони
* При создании брони сервис Bookings  посылает сообщение BookingCreated
* Сервис Events принимает его, делает требуемые проверки для мероприятия и в случае успеха уменьшает доступные места для мероприятия и посылает в ответ BookingConfirmed, либо BookingRejected в случае неудачи
* Сервис Bookings принимает эти сообщения и помечает брони соответствующими статусами
## Отмена брони
* При отмене брони сервис Bookins отправляет сообщение BookingCanceled
* Сервис Events принимает его и увеличивает количество доступных мест
## Удаление брони
* При отмене брони сервис Bookins отправляет сообщение BookingRemoved
* Сервис Events принимает его и увеличивает количество доступных мест
# Кэширование
Для уменьшения отклика системы в ендпоинты GET /Events/{id} и GET /Events/top добавлено кэширование. Кэширование осуществляется через **Redis**. При изменении данных происходит инвалидация кэша по следующим стратегиям:
* *Delete-on-Write* для отдельного мероприятия, чтобы не забивать память ключами которые могут и не использоваться, плюс к этому, данные о событиях меняются редко и небольшая рассогласованность (если она возникнет) в данных и кэше допустима
* *Update-on-Write* для топ 10. На список топ мероприятий влияют буквально все события происходящие в системе, и чтобы он отражал актуальные данные была применена эта стратегия
